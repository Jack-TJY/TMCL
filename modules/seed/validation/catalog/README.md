### 如何解释一行

- **1.12.2**：键保留原版大小写（例如 `/locate Temple`、`EndCity`）。值是本目录手工对照的语义名，**不是**该版注册 ID 或可单独输入的命令。Temple 包含沙漠神殿、丛林神庙、雪屋、沼泽小屋；现有图层只能选前两者。Mineshaft 的普通/恶地变体也不计作两条命令。
- **1.18**：键来自实际 Brigadier `locate` 子节点，值来自内置 configured structure feature 注册表，经默认维度生成器配置和可生成群系过滤；要塞单独检查原版环。例：`/locate endcity` 对应末地的 `minecraft:end_city`；下界的 `ruined_portal` 仅对应 `minecraft:ruined_portal_nether`。不要把配置名作为该版命令参数。
- **26.3**：`/locate structure` 的参数是 worldgen/structure 的 ID 或标签。5 种村庄、18 种废弃营地各有独立 ID；旧图层验证的是整组，不能据此宣称已能筛选 23 种变体。33 个标签（含用途标签）都不是额外建筑。结构集如 nether_complexes 是放置规则，不是新的命令目标。JSON 保留规范命名空间；默认 minecraft 命名空间的简写不另计。

### 离线复跑

在仓库根目录运行，输入是开发者自行提供的**官方服务端**，脚本先校验该版本指纹。Python 3.9+；旧版用 JDK 17/18，26.3 本次用 JDK 27。发布仓库不含 JAR、结构模板、群系参数、完整游戏报告或存档。

~~~sh
python modules/seed/validation/catalog/check.py 1.12.2 <server.jar> <JDK目录>
python modules/seed/validation/catalog/check.py 1.18 <server.jar> <JDK目录>
python modules/seed/validation/catalog/check.py 26.3 <server.jar> <JDK目录>
python -m unittest discover -s modules/seed/validation/catalog
cargo test --locked -p tmcl-seed --test locate_catalog
~~~

默认比较整个 JSON，任一成员、维度或目标变化即失败。传 `--output <新文件>` 可导出候选基准再审 diff。旧版探针运行在临时目录，不启动游戏服务：1.12.2 取命令补全，再以种子 0 调用三个默认维度生成器的定位入口；每个命令必须至少在一个维度实际返回位置。1.18 读取种子 1 普通预设的命令树和生成设置，不把配置存在误当成已生成某个起点。

26.3 用官方数据生成器的命令报告确认参数指向的注册表；从原版数据包联结结构注册、正权重放置条目和群系选择器。按普通预设使用主世界/下界的原版群系参数报告、末地的原版群系标签。另在真实普通单人世界的集成服务器线程运行 [Runtime26.sample](Runtime26.java)：解析定位命令、枚举活注册表和生成器的 possibleBiomes；核对全部 **52** 条维度归属及 **33** 个标签的 **66** 条成员关系。可在 26.3 复跑命令末尾追加 `--live-log <该次探针日志>`，逐项比较两种来源；仅在本地读取探针记录，不提交整份日志。该核查不宣称已逐座生成建筑。

### 2026-11-28 抽查发现与修复

26.3、种子 −1 的抽查先出现两处与官方 `/locate` 不一致，经排查后确认原因不同，均已修复并重新开放：

- **埋藏宝藏**：这是真实缺陷。先前把方块坐标除以 16 取区块时用了 C 的截断除法，负数会向 0 取整；宝箱 z=−135 被算成区块 −8，正确是 −9。桥接层已改为向下取整（与要塞环使用的同一个 `region()` 换算），种子 −1 的宝箱重新落在区块 (31,−9)。 修复后种子 −1、42、12345 的宝箱区块与引擎一致；种子 1 的原版 `/locate` 报 (36,11)，引擎给出更近的 (−28,−22)，维护者实机确认该处确有宝箱，说明原版命令再次跳过了较近位置。
- **试炼密室**：引擎没错。维护者实机确认引擎给出的区块 (1,−14) 确有试炼密室；原版 `/locate` 的环状搜索先命中了更远的 (21,5)，属于原版命令的近似行为，不能当作“最近”基准。

教训：**原版 `/locate` 只能证明“该位置存在”，不能证明“更近处不存在”**；比较时必须确认引擎给出的位置是否真实存在，而不是只比哪条输出更近。

### 2026-11-28 维度抽查（下界与末地）

`seed_map_query` 现在接受 `dimension`，下界与末地只返回结构起点，不提供群系瓦片。26.3、种子 −1：

| 维度 | 结构 | 官方结果 | 引擎 | 处理 |
| --- | --- | --- | --- | --- |
| 下界 | fortress | 区块 (4,18) | (4,18) | 开放 |
| 下界 | bastion_remnant | 区块 (−12,20) | (13,−12)；从该处再次 locate 为 0 格 | 开放 |
| 末地 | end_city | 区块 (26,83) | 修正后只报 (26,83)，误报 (−53,−36) 被拒绝 | 开放 |

末地城市此前误报的原因已查明（2026-11-29 修正）：上游 Seed Atlas 的版本一致性测试 `seedatlas-engine/tests_versions.c` 显示，末地城在群系检查之外还必须调用 `isViableEndCityTerrain()` 做旋转 5×5 最小高度检查；我们的桥接层只调用了 `isViableStructurePos` 与通用地形检查，漏了这一条，才把 (−53,−36) 当成有效起点。补上后 26.3 种子 −1 的官方起点 (26,83) 命中、误报被拒绝，末地城已开放。教训：引擎提供专用判定函数时，必须按上游测试的调用方式组合。

### 2026-11-28 变体家族抽查（海底废墟与废弃传送门）

这三类在 26.3 里有多个变体 ID（ocean_ruin_cold/warm、ruined_portal 六种主世界变体 + ruined_portal_nether），引擎按家族返回候选、由群系决定变体。抽查方式是：先取官方 `/locate` 报出的真实位置，再要求引擎在同一区块报出结果（存在性验证，不比“谁更近”）。26.3、种子 −1：

| 结构 | 官方方块（区块） | 引擎 |
| --- | --- | --- |
| ocean_ruin_cold | (336,336) → (21,21) | 命中 |
| ocean_ruin_warm | (−288,−144) → (−18,−9) | 命中 |
| ruined_portal | (32,1024) → (2,64) | 命中 |
| ruined_portal_desert | (−1856,−1072) → (−116,−67) | 命中 |
| ruined_portal_nether（下界） | (320,304) → (20,19) | 命中 |
| mineshaft / mineshaft_mesa（家族） | 26.3：(25,25) 与 (−58,−23) | 两处均命中 |

矿井同样按家族开放：桥接层改用引擎的 `getMineshafts` 逐区块 RNG，并保留 `isViableStructurePos`/地形检查；26.3 的基础变体与恶地变体官方位置都已命中。

因此界面按“家族”开放这四类：adventure 层包含该家族的全部变体；1.12.2 不支持，18 与 26.3 主世界/下界可用。**注意**：由于是家族层，界面不会分别列出 cold/warm 或各群系变体，文档与图例按家族说明。

### 缺口与实施顺序

剩余直接目标分别为 **5、13、48** 个（1.12.2 的 5 个含部分覆盖的 Temple）。下一批建议从三版主世界都存在、尚无产品图层的 **Mansion / mansion** 开始：先取原版有效起点和反例，再核实引擎的地形筛选误差。此后按放置算法拆批；下界/末地需单独验证生成器和坐标语义。未核验的项保留在分母中，不下发给 UI。
