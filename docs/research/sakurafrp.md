# SakuraFrp（樱花穿透）调研（M2-13）

调研日期：2026-10-29 · 调研人：claude-p2p

本报告供维护者决定 M2-14 的做法。**结论（2026-10-29 维护者选定）**：方案 A，运行时从官方接口下载并校验官方 frpc，用户填写自己的访问密钥，TMCL 通过官方开放 API 管理隧道；同时由维护者本人给官方发一封告知邮件（草稿另行提供，不放入仓库），不等回复也可以先开发。

> **重要：服务条款正文本次没有读到。** `https://www.natfrp.com/policy/tos` 是前端渲染的页面，抓取只拿到空壳；`api.natfrp.com` 在本调研环境的网络策略里被拦截。第 2 节列出了需要维护者本人打开条款逐条核对的问题，核对前不要把本报告当作“条款允许”的结论。

## 1. 已核实的事实

来源：SakuraFrp 官方帮助文档 [doc.natfrp.com](https://doc.natfrp.com/)，以及官方 GitHub 组织 [natfrp](https://github.com/natfrp) 下的仓库（`natfrp/api` 最近一次提交 2026-10-11）。

### 1.1 开放 API

- 官方仓库 [natfrp/api](https://github.com/natfrp/api) 发布了 OpenAPI 3.0 定义 `openapi.yaml`，标题 “SakuraFrp API”，版本 4.1.0，服务器地址 `https://api.natfrp.com/v4`，条款链接指向 `https://www.natfrp.com/policy/tos`，联系邮箱 `support@natfrp.cloud`。定义文件本身以 AGPL-3.0 发布。
- 认证：用户的**访问密钥**，可放在 `Authorization: Bearer <密钥>` 头，或作为 `token` 查询参数。访问密钥是专门给客户端登录用的密码，与账号密码不同，泄露后可在用户信息页重置（[frpc 基本使用指南](https://doc.natfrp.com/frpc/usage.html)）。
- 文档里**没有**看到第三方应用注册、App ID 或 OAuth 一类的机制，也没有写调用频率限制。
- M2-14 需要的接口都有：

| 接口 | 用途 |
| --- | --- |
| `GET /user/info` | 校验密钥、显示用户名与套餐 |
| `GET /nodes` | 节点列表；`flag` 字段的位含义见下 |
| `GET /tunnels`、`POST /tunnels` | 列出、创建隧道（`name`、`type=tcp`、`node`、`local_ip`、`local_port`，可选 `remote`） |
| `POST /tunnel/delete` | 删除隧道，`ids` 用逗号分隔，最多 10 条 |
| `POST /tunnel/config` | 取隧道配置文件 |
| `GET /system/clients` | 客户端下载信息：每个分类有版本号、发布时间，每个架构有 `url`、`hash`、`size`（示例下载域名为 `nya.globalslb.net`） |
| `GET /system/policy?type=tos` | 取服务条款正文与更新时间（**TMCL 可以在界面里直接展示条款**） |

- `GET /nodes` 的 `flag` 位：`1<<2` 允许创建隧道（满载为 0），`1<<3` 内地节点，`1<<5` 允许 UDP，`1<<9` 离线，`1<<11` 允许穿透公开游戏，等等。

### 1.2 公开游戏服务器限制（直接影响 TMCL 的设计）

`POST /tunnels` 的接口说明里写有一段“公开游戏服务器穿透限制警告”，要点如下：

- 公开游戏服务器指把连接方式发到论坛、服务器列表、QQ 大群等公共空间，或在 B 站、抖音、小红书等平台宣传招人的服务器。
- **公开游戏服务器只能使用专用节点**：节点 `flag & 2048 != 0`，或节点名包含“多线”（“三线”不算）。违反或隧道遭攻击，账户会被封禁且不退款。
- **小群熟人联机这类不公开的情况可以使用其他节点。**
- 接口还要求“帮助用户创建隧道的 AI 助手”在创建前确认用途并说明上述限制。这段文字是写给 AI 助手的，与 TMCL 的实现无关，但它说明官方很在意这条规则。

对 TMCL 的含义：创建隧道前必须问一句“这个房间会公开发布吗？”。选“会”时只列出满足 `flag & 2048` 的节点并提示条款；选“不会”时正常列出。这条应写进 M2-14 的验收。

### 1.3 frpc 客户端

- 启动方式：`frpc -f <访问密钥>:<隧道ID>[,<隧道ID>...]`，常用参数 `-n`（跳过更新检查）、`--disable_log_color`（v0.51.0-sakura-5.1 起）、`--log_level`（[frpc 用户手册](https://doc.natfrp.com/frpc/manual.html)）。
- 成功后日志会出现形如 `使用 >>frp-xxx.com:10086<< 连接你的隧道` 和 `或使用 IP 地址连接: >>1.2.3.4:10086<<` 的两行，可以从 `>>` 与 `<<` 之间解析出联机地址。退出码与日志格式没有正式文档，需要在 M2-14 实测并写 fixture。
- 官方帮助文档把 frpc 标为“仅限专业用户”，推荐普通用户用图形界面的官方启动器。
- **官方 frpc 不开源**：极客用户说明写明“我们的客户端软件并不开源”，但二进制没有加密或混淆（[geek.html](https://doc.natfrp.com/geek.html)）。文档里没有任何关于再分发 frpc 的说明，既没允许也没禁止。
- 官方也说明：上游开源 frpc 0.18.0 及以上可以用隧道配置文件连接 SakuraFrp 节点，官方会尽量保持兼容；但推荐使用官方客户端以获得最佳表现（[常见问题: 其他](https://doc.natfrp.com/faq/misc.html)、geek.html）。
- 下载文件附带的 `hash` 是 32 位十六进制，示例看起来是 MD5，只能防损坏不能防篡改；下载链接走 HTTPS，可以接受，但 TMCL 应同时校验大小和哈希。

### 1.4 第三方集成

- geek.html 明确说开发者可以根据 API 文档自己写启动器，并举了一个 Qt 实现的第三方启动器为例。这是目前能找到的、最接近“官方认可第三方客户端”的表述。
- 官方的启动器外壳与工具大多开源：`launcher-windows`（已归档）、`launcher-macos`（已归档）、`launcher-dsm`、`luci-app-natfrp`、`getfrp.sh` 都是 AGPL-3.0，`auth-guest` 是 GPL-3.0。
- [常见问题: 其他](https://doc.natfrp.com/faq/misc.html) 写明：不得使用、重标、改编 SakuraFrp 的创意项目、前端页面、用户条款、帮助文档等内容。TMCL 的界面与文案要自己写，不能照搬官方页面或文档。

## 2. 需要维护者本人核对的条款问题

请打开 <https://www.natfrp.com/policy/tos>（以及 `policy/content`、`policy/rule`）核对，结果填在第 7 节表格的“备注”里：

1. 是否禁止或限制第三方客户端、自动化调用 API？
2. 是否禁止再分发官方 frpc 二进制？（影响 A 与 A′ 的选择，见第 3 节）
3. 免费用户的隧道数、带宽、可用节点范围是多少？是否需要实名认证才能创建隧道？（本次没有核实，社区教程普遍提到需要实名，以条款和面板为准）
4. 是否有游戏联机相关的额外限制（除 1.2 节公开游戏服务器规则外）？
5. 条款的更新时间，便于以后复查。

## 3. 可选方案

| 方案 | 做法 | 优点 | 缺点 |
| --- | --- | --- | --- |
| **A** 运行时下载官方 frpc + 用户自己的密钥 + API（推荐） | 首次使用时调 `GET /system/clients` 拿下载地址、大小与哈希，下载到 TMCL 数据目录并校验；用户填访问密钥（存系统 keyring），TMCL 调 API 建删隧道，以子进程运行 frpc 并解析日志 | 用官方推荐的客户端，表现最好；**不再分发**闭源二进制，规避许可与再分发问题；用的都是官方公开的 API | 首次使用要多下一次；依赖官方 API 和下载地址不变 |
| **A′** 随安装包附带上游开源 frpc | 打包上游 [fatedier/frp](https://github.com/fatedier/frp) 的 frpc（Apache-2.0），用 `/tunnel/config` 取配置启动 | 离线可用；许可证明确且与 GPL-3.0 兼容 | 官方明说推荐官方客户端，上游版本缺少 sakura 专有协议的优化，出问题时官方可能不支持；安装包变大 |
| **B** 只引导用户用官方启动器 | TMCL 显示游戏端口和图文步骤，用户在官方启动器里建隧道，再把地址粘回 TMCL | 零集成风险，几乎零开发 | 体验差，失去“一键”的意义 |
| **C** 申请官方合作 | 维护者联系官方，询问是否有合作或推荐的集成方式 | 若获得认可，最稳妥，可能拿到专门的接入方式 | 结果和周期不可控；本身不产生功能，要和 A 或 B 搭配 |

## 4. 与 GPL-3.0 的许可证兼容性

| 组件 | 许可 | 与 TMCL（GPL-3.0）的关系 |
| --- | --- | --- |
| 官方 frpc | 闭源，再分发条款不明 | A 中 TMCL 只在运行时下载、作为独立程序调用，不链接、不随包分发。GPL-3.0 允许 GPL 程序调用独立的非自由程序（属于“聚合”而非衍生作品），所以没有许可冲突；风险只在服务条款层面 |
| 上游 frpc | Apache-2.0 | A′ 中可随包分发，Apache-2.0 与 GPL-3.0 兼容，附上许可证与 NOTICE 即可 |
| `natfrp/api` 的 OpenAPI 定义 | AGPL-3.0 | 按文档手写请求代码，不复制定义文件，不构成衍生作品。即使用它生成代码，AGPL-3.0 与 GPL-3.0 依第 13 条可以组合，但组合部分要遵守 AGPL 的网络交互条款，因此**建议手写接口代码，不复制或生成** |
| SakuraFrp 名称、文档、页面 | 见 1.4 | 界面中写“SakuraFrp（樱花穿透）”作为服务名说明即可，不用官方图标，不照搬文案 |

## 5. 推荐

**A，并由维护者发送 C 的告知邮件。**

- A 不分发任何闭源代码，许可证上最干净；用的是官方公开 API，geek.html 也表示欢迎开发者自己写启动器。
- 告知邮件的目的是在条款不明确的地方（第 2 节第 1、2 题）拿到书面答复。没有回复也可以继续开发，回复若有限制再调整。
- 如果维护者核对条款后发现明确禁止第三方调用 API，则退回 B。
- 对 M2-14 的补充（需要维护者同意后修订 PLAN.md）：
  - 创建隧道前询问是否公开，公开时只显示 `flag & 2048` 的节点；
  - 首次使用时在界面展示 `GET /system/policy?type=tos` 返回的条款并要求用户确认；
  - frpc 下载后校验大小与哈希，失败则删除重下；
  - 访问密钥只存 keyring，日志中脱敏，**永不**写进配置文件或诊断信息；
  - 关闭联机时删除本次创建的临时隧道（接口一次最多删 10 条）。
  - 填写密钥后读取 `GET /user/info` 的 `realname`（实名认证状态）字段；未实名时提示用户前往 SakuraFrp 官网完成实名并给出链接，TMCL 不收集任何身份信息（2026-10-29 维护者确认）。

## 6. 尚未解决与风险

- 条款正文未读到（见顶部说明）。
- 免费套餐限制与实名要求未核实。
- frpc 日志格式与退出码没有正式文档，官方更新可能改变日志，解析要宽松并有回退（解析失败时提示用户去官方面板查看地址）。
- 官方 API 与下载域名变化时，TMCL 需要发版跟进。
