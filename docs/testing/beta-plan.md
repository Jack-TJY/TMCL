# Beta 公测计划（M2-16）

本文件规定 `v0.2.0-beta.N` 的测试范围、反馈流程和每周整理方法。每轮测试结果追加到 [beta-matrix.md](beta-matrix.md)（第一轮开始时创建，格式同 [alpha-matrix.md](alpha-matrix.md)），每周整理记录追加到本文件末尾的“周报”一节，不改旧记录。

## 1. 版本与发布条件

- 版本号：`0.2.0-beta.N`，tag 为 `v0.2.0-beta.N`，在 GitHub Releases 发布为预发布（Pre-release）。
- 发布方式：维护者手动执行。`build.yml` 不会自动发布，安装包由它构建后，用 `gh release create` 上传（见 §6）。
- `v0.2.0-beta.1` 的发布条件，全部满足才发：
  1. M2-12b（Scaffolding 信令与房主 / 房客流程）和 M2-15（联机页）已合并到 `main`；
  2. 维护者在真机上按 §3 跑完第 1 轮，结果记入 `beta-matrix.md`；
  3. 第 1 轮没有未修复的 P0。
- 之后的 `beta.N+1`：有 P0 修复时尽快发；否则每 1–2 周发一次，由周报（§5）决定。

## 2. 缺陷等级

沿用 Alpha 的等级，测试记录与 Issue 中都用这套等级：

| 等级 | 含义 | 处理 |
| --- | --- | --- |
| P0 | 主流程不可用：无法安装、无法启动、数据丢失（存档、实例、皮肤库、`options.txt` 被破坏）、泄露令牌或访问密钥、联机暴露了游戏端口以外的端口 | 发布前必须修复；已发布的版本出现时，修好后立即发下一个 beta |
| P1 | 功能可用但有明显问题，或只影响个别版本 / 加载器 / 平台 | 记为已知问题，随下一个或下下个 beta 修复 |
| P2 | 体验问题、文案、布局 | 排期修复 |

GitHub 上 `P0` / `P1` / `P2` 标签目前表示“属于哪个里程碑”（见 [labels.md](../labels.md)），不是缺陷等级。缺陷等级用 `severity:P0`、`severity:P1`、`severity:P2` 标签。

**结束条件（门槛 G3）**：连续两个 beta 版本没有新的 P0 / P1 缺陷，且所有 P1 模块要么完成、要么由维护者明确推迟。

## 4. 反馈流程

1. **入口**：所有问题都进 GitHub Issues，用“问题反馈”模板并附诊断信息包；功能建议用“功能建议”模板。其他渠道（群聊、私信）收到的问题由维护者转成 Issue，链接原始反馈。
2. **涉及安全的问题**（令牌或访问密钥泄露、联机暴露额外端口）不要公开提交：在仓库 Security 页用“Report a vulnerability”私下报告（维护者需先在仓库设置中打开 Private vulnerability reporting）。按 P0 处理。
3. **分诊**（维护者，48 小时内）：
   - 加 `module:*` 标签（模板中的“相关模块”可作参考）和 `severity:P0/P1/P2`；
   - 信息不足时评论要具体信息并加 `needs-info`，14 天无回复关闭；
   - 重复的问题标 `duplicate` 并链接原 Issue；
   - P0 当天开修复 PR，PR 描述写 `Fixes #编号`。
4. **修复与验证**：修复合并后 Issue 自动关闭，在 Issue 中写明“将在 `v0.2.0-beta.N+1` 中发布”；新版本发布后请报告者复测，复测失败重新打开。
5. **记录**：每轮测试中发现的缺陷登记到 `beta-matrix.md` 的缺陷表，编号接着 Alpha 的 D 编号写（Alpha 用到 D11，Beta 从 B1 开始），并链接 Issue。

## 5. 每周整理

每周一整理上一周（周一 00:00 到周日 24:00，北京时间）的反馈，结果追加到本文件末尾“周报”一节。

1. 拉取本周新建和有更新的 Issue：

   ```sh
   gh issue list --repo Jack-TJY/TMCL --state all --limit 200 \
     --search "created:>=YYYY-MM-DD" --json number,title,labels,state
   gh issue list --repo Jack-TJY/TMCL --state open --label bug \
     --search "updated:>=YYYY-MM-DD" --json number,title,labels
   ```

2. 补齐分诊：没有 `severity:*` 或 `module:*` 标签的 Issue 按 §4 处理；合并重复项。
3. 按模块统计新增与关闭数，列出所有未关闭的 P0 / P1。
4. 看诊断包里的共性：同一错误码、同一平台或同一游戏版本反复出现时合并为一个 Issue。
5. 决定：
   - 是否发下一个 beta（有已修复的 P0，或距上次发布满两周且有已合并的修复）；
   - 哪些 P1 进入下一个 beta；
   - 是否满足 G3（连续两个 beta 没有新的 P0 / P1）。
6. 周报格式：

   ```md
   ### 第 N 周 · YYYY-MM-DD 至 YYYY-MM-DD

   - 当前版本：v0.2.0-beta.N
   - 新增 Issue：X（bug Y，建议 Z）；关闭：X
   - 未关闭 P0：#…；未关闭 P1：#…
   - 按模块：resources X、sync X、skin X、p2p X、sakura X、其他 X
   - 共性问题：…
   - 决定：发 / 不发 beta.N+1；下一版包含 #…、#…
   - G3：第几个没有新 P0 / P1 的 beta
   ```

## 6. 发布步骤（维护者手动）

1. 确认 §1 的发布条件。版本号已在 `Cargo.toml`（`[workspace.package]`）、`Cargo.lock`、`package.json`、`ui/package.json`、`src-tauri/tauri.conf.json` 中改好，且 [CHANGELOG.md](../../CHANGELOG.md) 中该版本的“草稿”标记已去掉、日期已填。
2. 在 `main` 上打 tag 并推送：`git tag v0.2.0-beta.N && git push origin v0.2.0-beta.N`，`build.yml` 会构建三平台安装包。
3. 构建完成后下载产物，用 `gh release create v0.2.0-beta.N --prerelease --title "v0.2.0-beta.N" --notes-file <从 CHANGELOG 摘出的本版内容> <安装包…>` 发布。
4. 发布后在 W10 上用 Releases 页面的安装包快速跑 A1，并确认首页“更新日志”能看到新版本。
5. 下一个 beta 开发开始时，把版本号改为 `0.2.0-beta.N+1`，在 CHANGELOG 中新开一节草稿。
